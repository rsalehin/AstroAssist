Technical reference

A provenance-first, multi-agent
research workbench for astronomers

AstroAssist turns natural-language questions into reproducible, provenance-tracked scientific answers assembled from astronomical archives, Astropy calculations and the literature — run entirely on your own machine. This page explains the architecture, the data-flow, the tech-stack, the end-to-end story, and how it would be deployed and operated for a small research group.

01 What it is

A locally-run workbench — think “Jupyter + Aladin + a research chat” — that lets a working astronomer ask a question in plain language and get an answer where every number has a unit, an uncertainty, a source, and a re-runnable query behind it.

🔭

For research astronomers

PhD students, postdocs and staff who already live in SIMBAD, VizieR, ADS and Python and distrust anything that can’t show its sources.

🧬

Provenance by construction

Every scientific output is a typed artifact carrying a full lineage record. A tool that returns a bare float is a bug.

♻️

Reproducible

A whole session exports as a runnable notebook + data + queries + bibliography that executes standalone.

The day-one story

🌟 Investigate AD Leo
Resolve the object, retrieve the best current astrometry and stellar properties, calculate distance and tangential velocity, find available TESS observations, display a light curve, identify flaring activity, find recent papers on its magnetic activity, and produce a research summary in which every retrieved number, calculated number, plot, query and citation can be inspected and reproduced. If that runs end-to-end with full provenance and exports as a bundle, v1 is real.

02 Principles & scope

Product principles (ordered)

  1. Correctness — a beautiful hallucinated table is a product failure.
  2. Provenance — sources that disagree are shown side by side, never silently reconciled.
  3. Reproducibility
  4. Uncertainty made visible
  5. Inspectability — queries, code, trace
  6. Speed, then Aesthetics

Non-negotiable engineering rules

  • 🔢 No naked numbers — every quantity is an Astropy Quantity/SkyCoord/Time.
  • 🧾 No artifact without provenance.
  • 🤖 Agents return artifacts, not prose — only synthesis writes text, citing artifact ids.
  • 🔌 Sources are tools; agents are reasoning roles.
  • 🔍 Every external query is inspectable (stored ADQL/URL/params/raw).
  • 🪟 Windows must not break — core installs on all three OSes.

Explicit non-goals (v1)

Manuscript generation · proposal writing · telescope control · raw data reduction pipelines · HPC/cluster jobs · arbitrary web browsing by the agent · teams / shared workspaces / RBAC · a connector marketplace. A plugin spec is in scope; a marketplace is not.

03 Architecture

A single-user, local process: a FastAPI backend serves a React workbench and orchestrates a LangGraph state machine. Agents are reasoning roles; archives and calculations are tools. Everything a tool produces is a typed artifact with provenance, persisted to a per-workspace store and streamed to the UI as it happens.

Key trade-off
Curated typed tools limit flexibility but make determinism, provenance and evaluation possible. A Python “escape hatch” restores flexibility — behind a human approval gate and a resource-limited kernel. A planner + DAG is heavier than a plain ReAct loop, but buys parallelism, preflight cost estimates, and an inspectable plan artifact.

04 Request lifecycle

Every message flows through nine stages. Stages that could be expensive or risky raise a human-in-the-loop interrupt before proceeding.

StageWhat happens
IngestMessage arrives with a thread id; artifacts referenced via @id are attached.
ResolveNew identifiers hit the object resolver (session cache → SIMBAD → Sesame → NED for extragalactic context).
RouteA cheap model classifies intent (identity / catalog / observation / literature / compute / plot / plan / mixed).
PlanThe planner emits an explicit DAG of typed steps with declared inputs/outputs; the plan is itself an artifact.
PreflightEach step estimates cost (queries, rows, bytes, duration). Steps over threshold create an approval interrupt.
ExecuteSteps run as graph nodes; tools return typed artifacts; raw payloads go to disk and are referenced by id (never dumped into model context).
SuperviseFailures trigger bounded self-correction (≤2 for query errors) or replanning; capability-aware fallback with explicit “not retrieved” reporting.
SynthesizeA strong model writes the answer from artifact summaries only, citing artifact ids; a post-check rejects numerals not traceable to an artifact.
PersistArtifacts, queries, code and trace entries are stored; the bibliography is updated.

05 Data flow — end to end

The backend runs the graph and maps LangGraph events onto a streaming schema the UI consumes over Server-Sent Events. Below is the concrete path that ships today (the M0 echo round-trip) — the same shape every future feature reuses.

Streaming event schema

// each SSE "data:" line is one JSON object with a "type"
{"type":"trace", "step":"execute", "agent":"compute", "tool":"echo", "duration_ms":0}
{"type":"artifact", "artifact":{"id":"art_…", "kind":"ScientificValue", "summary":"Echo of: hello", …}}
{"type":"token", "text":"Echo complete — …"}
{"type":"done", "thread_id":"thr_…"}

The frontend parses these events (CRLF-safe), appends streamed tokens to the assistant message, and renders each artifact as a card inline in chat and in the viewer. Interrupts arrive as an interrupt event and block only the affected branch.

06 Data model & provenance

Everything scientific is a typed artifact (Pydantic) carrying a Provenance record. Physical numbers use Astropy wrappers so units survive serialization; tabular and binary payloads live on disk and are referenced by path.

Provenance record

class Provenance:
  artifact_id, created_at
  method   # catalog_measurement | observation
           # | derived | literature | fit | …
  source, source_version, source_record_id
  query_id            # the QueryArtifact
  inputs: list[str]   # lineage edges
  tool, code_hash, parameters
  citation_keys, quality_flags, warnings

Artifact kinds

A discriminated union keyed by kind:

ResolvedObjectScientificValue CatalogTableObservationList LightCurveSpectrum ImageFitResult PlotArtifactLiteratureSet CitationSetQueryArtifact CodeArtifactPlanArtifact JobArtifact

Each also carries a ≤512-char summary — the only thing the LLM ever sees.

♻️ Reproducibility is a feature
Artifacts are immutable; edits create new artifacts with a parent_id. The lineage graph (provenance.inputs) is walked at export time to emit a dependency-ordered notebook + data/ + queries/ + references.bib + provenance.json that runs standalone.

07 Agents & orchestration

Sources are tools. Agents are reasoning roles split by scientific domain — never one agent per archive. The graph is a LangGraph StateGraph with a typed state, a SQLite checkpointer keyed by thread id, and interrupt()-based HITL.

RoleResponsibilityTools / sources (v1 → later)
Routerclassify intent, pick profilecheap model
Plannerbuild a typed DAG, declare I/O, estimate coststrong model + registries
Object & Catalogidentity, astrometry, photometry, crossmatchSIMBAD, Sesame, Gaia, VizieR → NED, SDSS…
Observationfind/inspect reduced productsMAST → ESO, HEASARC…
Literaturepapers, citations, bibliographyADS → arXiv, local RAG
Time-Domainlight curves, periodograms, flareslightkurve/MAST → ZTF, AAVSO…
Computecurated deterministic tools + Python escape hatchAstropy, SciPy, astroplan
Visualizationplot-spec construction, Aladin statematplotlib, Plotly
Supervisordetect failures, self-correct, replan, fallback—
Synthesisfinal answer from summaries; cites ids; flags disagreementstrong model

Model access is pluggable via a ModelProvider protocol with profiles (economy / balanced / research / local) mapping each role to a concrete (provider, model). Adapters exist for Anthropic, OpenAI, OpenAI-compatible, Ollama and vLLM. A deterministic mock provider replays scripted responses so every test and e2e run is offline and key-free.

11 Testing & determinism

make check is the single gate. No live network in unit/component/e2e — the mock model provider plus recorded archive fixtures make the whole request path run offline with no API keys.

LayerToolScope
Lint / typesruff, mypy (strict on core/), eslint, tsceverything
Unitpytest + pytest-recordingtools, connectors, artifacts, coords, units, cache
Componentvitest + React Testing Libraryevery card/panel renders from a fixture artifact
E2EPlaywright vs serve --profile mockmessage → stream → cards → approval → export
Contractpytest -m liveone small live query per source (nightly/manual)
Benchmarkastroassist eval runscientific correctness, deterministic evaluators

Frontend fixtures are generated from the Python models (astroassist eval fixtures --ts) so UI and backend share exactly the same shapes. Deterministic evaluators dominate LLM judges for scientific quantities — assertions check unit, value within tolerance, and provenance completeness.

12 Deployment illustrative

AstroAssist is single-user and local by design. For a group of ~20 people, two deployment shapes make sense. The reproducibility and provenance guarantees don’t change; only where the process runs and how it’s isolated do.

Option A · recommended

Per-workstation local install

Each researcher installs and runs their own instance. Zero shared infrastructure, perfect data isolation, credentials in each user’s OS keyring, data under ~/.astroassist.

# one command, no build step
uv tool install astroassist   # or: pipx install astroassist
astroassist serve             # opens the workbench in the browser
# update: uv tool upgrade astroassist

Best fit for v1: matches the design, nothing to operate, works offline for cached analysis.

Option B · shared appliance

One internal server, per-user instances

A small Linux VM on the lab LAN runs the container behind a reverse proxy that adds TLS and authentication (the app itself has no auth — that is a deliberate non-goal, so the proxy provides identity). Because v1 is single-user, run one lightweight instance per person (routed by sub-path/subdomain) rather than a single shared workspace.

Best fit when users are on thin clients, or you want central backups, a shared archive cache, and one place to update.

Container image (illustrative Dockerfile)

FROM node:22-slim AS web
WORKDIR /web
COPY frontend/ .
RUN npm ci && npm run build            # → /web/dist

FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
WORKDIR /app
COPY . .
COPY --from=web /web/dist frontend/dist  # FastAPI serves the built UI
RUN uv sync --extra dev --frozen
EXPOSE 8765
ENV ASTROASSIST_DATA_DIR=/data
HEALTHCHECK CMD curl -fsS http://127.0.0.1:8765/api/health || exit 1
CMD ["uv","run","astroassist","serve","--host","0.0.0.0","--port","8765","--no-open-browser"]
Security note
The app binds 127.0.0.1 by default and has no built-in auth. Never expose raw uvicorn to the LAN — always front it with the reverse proxy for TLS + authentication, and keep generated-code execution behind the HITL gate and a resource-limited kernel.

Continuous delivery (recommended)

  1. Tag v* → build frontend, build wheel (uv build)
  2. Build & push multi-arch image to ghcr.io (or internal registry)
  3. Publish wheel to PyPI via OIDC trusted publishing (no stored token) + GitHub Release
  4. Deploy: SSH to appliance → docker compose pull && up -d (or Watchtower)
  5. Workstations: uv tool upgrade astroassist (optionally automated)

Release workflow sketch

on: { push: { tags: ["v*"] } }
jobs:
  build-and-publish:
    steps:
      - uses: actions/checkout@v4
      - run: cd frontend && npm ci && npm run build
      - run: uv build                       # sdist + wheel
      - uses: pypa/gh-action-pypi-publish    # OIDC, no secrets
      - run: docker buildx build --push \
             -t ghcr.io/rsalehin/astroassist:${GITHUB_REF_NAME} .
      - uses: softprops/action-gh-release    # attach wheel + notes

Promotion gates: CD only runs after the full CI matrix is green on the tagged commit; roll back by re-pinning the previous image tag or uv tool install astroassist==<prev>.

14 DevOps & operations

🔐

Secrets & config

Tokens live in the OS keyring (workstation) or Docker/compose secrets (appliance) — never baked into the image or logged. Config via ~/.astroassist/config.toml + ASTROASSIST_* env.

📈

Observability

Structured JSON logs (structlog, secret-redacted) → stdout/file → optional Loki/Promtail. Readiness at /api/health. LangSmith tracing opt-in and redacted.

💾

Backups

Snapshot ~/.astroassist/workspaces/<ws> (SQLite + DuckDB + artifact files + checkpoints) nightly to the NAS with restic/borg. Each project also exports a self-contained reproducibility bundle.

🤝

Politeness to archives

Per-connector RatePolicy (concurrency, rps, backoff+jitter, honor Retry-After, circuit breaker) and TTL caching. A shared appliance cache keeps 20 users from hammering SIMBAD/Gaia.

🧪

Sandboxing

Generated Python only runs after HITL approval, in a workspace-scoped kernel with resource limits. One kernel per user instance on the appliance.

🔄

Updates & supply chain

Renovate/Dependabot, pinned lockfiles, pip-audit/npm audit in CI, SBOM on release. DB migrations: SQLModel create_all today; Alembic when schemas evolve.

Operational SLOs for a 20-user install

ConcernTarget / practice
AvailabilityBest-effort office-hours; systemd Restart=on-failure; health-check gated container restarts
BackupsNightly, 30-day retention; quarterly restore test
Capacity~1 vCPU + 1–2 GB per active instance; archive queries are I/O-bound, not CPU-bound
Data isolationPer-user volume + kernel; no cross-user workspace access (multi-tenancy is a v1 non-goal)
